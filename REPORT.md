## 1(A) Python iPerf3 Client

Our Python client implements the iperf3 protocol directly, without the iperf3 program: it opens the control connection and exchanges the JSON test parameters, opens the data connection, sends data for the chosen duration, and ends the test the way iperf3 expects ([run_test](code:client.py#def run_test), [protocol.py](code:protocol.py#def receive_state)). Timeouts, busy servers ("access denied"), rejected parameters, bad JSON, and dropped connections end the test with a logged error instead of hanging ([try_run_test](code:client.py#def try_run_test)).

## 1(B) Destination Selection

The client tests `-c` random servers (default 10) from the iperf3serverlist.net list and replaces a failing server with the next untried one, up to `-a` attempts, reporting any shortfall ([run_destinations](code:destinations.py#def run_destinations)). Each test records its server address and port. The Q1 run completed all three requested destinations in five attempts: one candidate returned ACCESS_DENIED and another refused the connection; both were replaced. For Q3 it took 8 candidate servers to get 3 where all nine tests succeeded; 23 of 72 tests failed, mostly because servers were busy, timed out, or dropped the connection.

## 2(A) Recording TCP Statistics

Q2 uses CUBIC, the default on our host (kernel `6.18.54.1-microsoft-standard-WSL2`); the algorithm actually used is read back from the socket and saved with every sample. At each goodput sample the client reads `TCP_INFO` from the data socket and saves one CSV row per interval with the time, goodput, `snd_cwnd`, smoothed RTT, `rttvar`, retransmissions, pacing and delivery rates, and the cumulative counters, plus the run ID, destination, algorithm, and units ([save_run](code:measurement.py#def save_run)).

- **Decoding:** the kernel returns Linux's `struct tcp_info` as raw bytes; we unpack its first 248 bytes field by field with Python's `struct` module ([tcp_info.py](code:tcp_info.py#TCP_INFO_FIELDS:)).
- **Interval values:** cumulative counters are differenced between samples; cwnd and RTT are read at the end of each interval.
- **Loss signal:** segments retransmitted per interval (the increase in `tcpi_total_retrans`), an estimate of loss.

## 2(C) Observations

**What each metric means**

- **Congestion window:** how many segments TCP allows to be unacknowledged at once. When it is the limit, goodput ≈ window × segment size ÷ RTT, so a bigger window means more goodput. In congestion avoidance CUBIC grows the window slowly and cuts it by 30% after a loss [2].
- **RTT:** how long data takes to be acknowledged. The lowest RTT is roughly the path's travel time; anything above it is time spent waiting in queues. With the same window, a higher RTT means lower goodput.
- **Loss signal (retransmissions):** after a loss CUBIC shrinks its window, so goodput should drop and then recover slowly.
- **Goodput:** how fast our data is actually acknowledged. It is the result of the other three.

**What we saw**

Start-up: The window grew from 88 to 4,191 segments in the first 1.5 seconds. Slow start then ended without any loss (the slow-start threshold was set equal to the window). This matches Linux CUBIC's HyStart, which leaves slow start as soon as RTT starts to rise.

The window was not the limit at first: From 1.5 to 4 seconds the window allowed about 355 Mbit/s, but goodput was only 160–176 Mbit/s. Only about 2,000 segments were actually in flight and almost nothing was waiting to be sent, so our sender, not the network, was the bottleneck. Linux does not grow a window that is not being used, which is why it stayed flat.

Losses cut the window: Retransmissions at 4.5, 5, 7, 9, 10, and 12 seconds each cut the window to about 70% of its size (for example 1,568 → 1,102 and 906 → 635 segments).

After that, goodput followed the window: From 5 seconds on, the window was full and goodput matched window × segment size ÷ RTT within a few Mbit/s (121 vs 125, 62 vs 61, 48 vs 49 Mbit/s). That is why the window–goodput scatter in Figure 3 is almost a straight line.

Anomaly, losses without extra delay: RTT stayed at 127–130 ms, within 3 ms of its minimum, for the whole test, so the RTT–goodput scatter is a vertical band. The losses therefore did not come from a queue filling up, which would have raised RTT; a small router buffer, a rate limiter, or random loss on the path would look like this. CUBIC still treated each loss as congestion, and goodput fell from 176 to about 50 Mbit/s.

Anomaly, slow recovery: Between losses the window grew by only about 14 segments per round trip, so 15 seconds was not long enough to get back to the earlier rate.

## 3(A) Compare CUBIC, Reno, and BBR

We compared CUBIC, Reno, and BBR at three destinations, using three 60-second runs per algorithm and one-second sampling: 27 matched runs. Each algorithm was set on the data socket before connecting, read back, and recorded ([data_connection](code:client.py#def data_connection)). The host ran Linux `6.18.33.2-microsoft-standard-WSL2` and Python 3.14.8. Its recorded library versions were matplotlib 3.11.2 and pydantic 2.13.5.

Destinations were shuffled with seed 422. Algorithm order rotated across repetitions, placing each algorithm first, second, and third once per destination ([run_comparison](code:comparison.py#def run_comparison)). Dallas used BBR/CUBIC/Reno, CUBIC/Reno/BBR, then Reno/BBR/CUBIC; Netfiber began with the third of these orders and the IP destination with the second. Tests ran sequentially with a two-second pause. Dallas was the first complete group and became the representative without selecting by throughput. Five incomplete destination groups were excluded; their partial measurements and all failures remain in the logs.

Goodput uses changes in acknowledged bytes divided by actual elapsed time. Algorithm means average three duration-weighted run means; ± values are sample standard deviations across runs. RTT is the mean sampled smoothed RTT. Retransmission totals are a loss proxy, not packet-loss probabilities ([run_statistics](code:comparison_plots.py#def run_statistics)). The CSV summaries additionally provide per-run minimum, median, arithmetic mean, and linearly interpolated P95 goodput.

**Observations**

Dallas: Reno delivered 281.30 Mbit/s, CUBIC 273.96, and BBR 269.79. BBR had the lowest mean RTT (64.53 ms), while Reno had the highest (73.65 ms). Thus Reno's modest throughput advantage came with higher measured delay. Reno's median cwnd rose from 1,982 to 7,854 segments across repetitions while throughput stayed near 279–284 Mbit/s. A larger window budget did not yield proportionally more delivery. Minimum filtered RTT was about 29–32 ms; higher observed RTT is consistent with queueing or other variable delay, including reverse-path delay.

Netfiber: With minimum RTT around 170–174 ms, Reno and CUBIC achieved similar throughput (119.07 versus 118.08 Mbit/s). Their difference was small relative to CUBIC's run variation. BBR averaged 106.59 Mbit/s and slightly lower RTT. Its third run delivered only 86.57 Mbit/s with 396 retransmissions, compared with 115.56 and 117.63 Mbit/s in its first two runs. RTT stayed close to baseline during much of the slowdown, showing why a loss signal is useful alongside RTT.

IP destination: Reno and CUBIC were effectively tied (163.52 versus 163.12 Mbit/s), with run standard deviations of 11.80 and 17.51 Mbit/s. BBR averaged 147.47 Mbit/s and had more variable RTT. In its first run, the interval at about 50 seconds had zero acknowledged goodput and a 1,559.64 ms RTT, with retransmissions increasing. The transfer still completed. This stall contributes to the averages; it was not removed as an outlier.

Across these paths, Reno had the highest mean throughput, BBR had lower mean RTT on two paths, and neither CUBIC nor BBR established a throughput win. These are observed operating regimes, not universal rankings. Reno's additive growth [1], CUBIC's faster growth on suitable large-bandwidth-delay paths [2], and BBR's bandwidth/RTT model [3] explain their intended behavior, but do not prove what caused differences between sequential Internet tests.

For a window-limited flow, rate is approximately cwnd × MSS / RTT. In Dallas's third Reno run, median window budget was about 11.37 MB, versus a 1.09 MB achieved-rate × minimum-RTT proxy. The proxy is not an independent bottleneck-capacity estimate, and cwnd is not actual bytes in flight. Server limits, receiver windows, pacing, or path capacity can limit delivery.

Public routes and cross-traffic changed between tests; rotating order cannot remove that variation. Three runs and one-second samples also limit conclusions. These single-flow tests do not establish fairness.

## 3(B) Proposed Congestion Control Algorithm

The Assignment 2 observations motivated combining delay, goodput, and loss. At Dallas, a larger window did not produce proportionally more goodput, motivating a check of delivery progress alongside delay. At Netfiber, a low-throughput run had many retransmissions despite similar mean RTT, motivating a separate loss response. The IP-path stall combined increased RTT with stalled ACK progress, motivating the delay-and-goodput backoff condition.

The controller starts with cwnd = 10 segments, subject to kernel limits, and an initially unlimited slow-start threshold. It keeps the minimum valid RTT since connection start and compares each eligible interval's goodput with the previous eligible interval. Goodput uses newly acknowledged bytes divided by actual elapsed time. At most one normal window decision occurs per RTT after ACK progress, outside recovery. Application- and receiver-limited intervals are skipped; the kernel implementation also skips send-buffer-limited intervals and intervals that are not congestion-window limited.

```
State: slow_start = true; previous_goodput = unset
On a new loss-recovery episode:
    request ssthresh = max(2, floor(cwnd / 2))
    let Linux apply recovery once using that threshold
    slow_start = false; clear previous_goodput and interval accounting
On a retransmission timeout:
    let Linux apply its normal timeout window and recovery
    slow_start = true; clear previous_goodput and interval accounting
Once per RTT with new ACK progress, outside recovery:
    update minimum_RTT and measure goodput
    if application limited or receiver-window limited:
        clear previous_goodput; finish interval
    if slow_start and cwnd < ssthresh and RTT <= 1.10 * minimum_RTT:
        cwnd += min(newly_acked_segments, cwnd)
    else:
        slow_start = false
        if RTT > 1.25 * minimum_RTT and previous_goodput is valid
           and goodput <= previous_goodput:
            cwnd = max(2, floor(0.90 * cwnd)); ssthresh = cwnd
        else if RTT <= 1.10 * minimum_RTT:
            cwnd += 1
        else:
            hold cwnd
    obey the kernel window limit
    previous_goodput = goodput; finish interval
```

The range between 10% and 25% RTT inflation holds the window to avoid reacting to every small delay change. High-delay backoff also requires non-improving goodput. The 10% reduction has a minimum of two segments; Linux's timeout recovery can instead reduce the window to one. The thresholds are heuristics, not tuned or validated values. `Q3_DESIGN.md` gives the full design.

Assuming persistent flows, equal RTTs, and a shared bottleneck, additive growth and proportional reductions may encourage similar windows. Fairness and convergence are not guaranteed: unequal RTTs favor different update rates, delay-sensitive flows can yield to loss-based flows, and an outdated minimum RTT or noisy goodput readings can affect decisions. Repeated increases and decreases may produce oscillation. These baseline measurements motivate the design; the custom controller's implementation and evaluation are in Assignment 3.

## Reproduction

Everything runs from `main.py`; the README documents the commands and options (`-c` destinations, `-t` duration, `-g` sampling interval, `-r` repetitions), and the `Dockerfile` (`FROM ubuntu:24.04`) runs the same pipeline.
